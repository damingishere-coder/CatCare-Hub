# P20：龙岗默认地址与电动自行车路线

## 背景

订单地址可能只包含街巷和门牌，缺少城市、行政区时高德无法稳定定位；当前路线又固定使用驾车接口和驾车距离矩阵，与实际电动自行车上门方式不符。

## 目标

- 智能粘贴地址时只对缺失行政区的内容补充“深圳市龙岗区”。
- 旧订单不改库，地图查询时对缺失行政区的地址执行同样补全。
- 真实路线改为高德电动自行车路线，多任务逐段计算并合并。
- 任务顺序使用本地快速推荐，最终距离、时间和折线仍来自高德真实道路。

## 允许修改范围

- `frontend/src/features/orders` 下的地址解析、订单表单及其测试。
- `frontend/src/features/plans` 和管理页中的路线类型、展示文案及其测试。
- `backend/app/maps`、订单定位与路线推荐服务、相关 Schema 和测试。
- `.env.example`、`README.md` 中非敏感的默认城市和路线说明。
- 本任务文档。

## 禁止修改范围

- 不读取、输出或提交 `.env`、API Key、Token、Cookie、浏览器数据或真实数据库内容。
- 不批量改写历史订单地址，不新增数据库字段或迁移。
- 不把明确的外地或非龙岗地址强制改为龙岗。
- 地图查询不发送单元、房间、姓名、电话、微信、门禁、钥匙、备注或照片。
- 不在浏览器或真实连接验收中修改订单 #2 或其他真实业务数据。
- 不使用驾车矩阵冒充电动车推荐，不执行高成本的逐地点对 GPT 矩阵。
- 不覆盖、清理、暂存 `.codemap/`、`PROJECT_AUDIT.md` 或其他任务外文件。
- 不强推、不重写 Git 历史、不改变仓库可见性或权限。

## 已确定实现要求

1. 地址规范化后，缺少城市和行政区时补“深圳市龙岗区”；只有“深圳市”时补“龙岗区”，只有“龙岗区”时补“深圳市”。
2. 已有完整龙岗前缀不得重复；明确存在其他城市或行政区时保留原文。
3. 新粘贴地址把补全后的行政区保存在详细地址；小区、楼栋、单元、房间仍按现有字段拆分并允许人工修改。
4. 后端只在地图查询地址中对旧订单虚拟补全行政区，订单展示和数据库原值不变。
5. 高德地理编码城市范围默认使用“深圳市”，`CATCARE_MAP_CITY` 仍可覆盖默认值。
6. 高德路线使用 `/v5/direction/electrobike`，按“家 → 任务 1 → 任务 2 …”逐段请求并累计距离、耗时、折线。
7. 不调用 `/v3/direction/driving` 或 `/v3/distance`；顺序推荐使用本地最近邻，最终当前路线和推荐路线均以真实电动车道路重新计算。
8. 路线工作区公开 `transport_mode: "electrobike"`，界面明确显示电动车路线与本地快速推荐。
9. 高德 URI 导航使用 `mode=ride`，不携带驾车专用 `policy`。
10. 不新增依赖、数据库字段或迁移。

## 验收标准

- 无行政区、仅有市、仅有区、完整龙岗、其他城市/区、全角字符和重复粘贴均正确处理。
- `长坑三巷21号1312房` 解析为详细地址 `深圳市龙岗区长坑三巷21号` 和房间 `1312房`。
- 旧订单的地图查询包含缺失的默认行政区，但数据库地址不变，单元和房间不进入地图请求。
- 电动车 Adapter 正确解析高德响应，多任务逐段调用并正确汇总距离、时间与折线。
- 路线 API 返回 `transport_mode="electrobike"`，不请求驾车路线或驾车矩阵，推荐来源为本地快速推荐。
- 手机导航链接使用 `mode=ride`。
- 后端完整测试、前端测试、lint、类型检查和构建全部通过。
- 真实高德验收只发起不写业务数据的电动车路线请求。
