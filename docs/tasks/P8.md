# P8｜收款记录任务文件

## 背景

P0-P7 已完成 Windows 本地 Web 管理后台、客户与多猫档案、订单、按天计划、路线、任务执行和工作台。`Order` 已保存应收、已收与付款状态，`Payment` 已保存订单、客户、金额、方式、状态、时间和备注，但当前没有收款 API 或页面，且 P7 的待收款读取 `Order`、本月收入读取 `Payment`。P8 必须建立真实登记闭环，使之后新增的收款流水与订单金额在同一事务中保持同步。

正式依据为《猫咪喂养登记系统-开发执行文档.md》第 13 节与 P8：开发 `/admin/payments`，覆盖应收、已收、待收、收款方式、收款时间、登记收款、订单关联和简单汇总；首版方式为微信、支付宝、现金、其他。

## 目标

- 建立隐私最小化的收款汇总、待收订单和收款流水 API。
- 将 `/admin/payments` 从占位页升级为可用的 PC 本地收款页。
- 支持同一订单多次部分付款和恰好付清，并原子同步 `Payment` 与 `Order.paid_amount/payment_status`。
- 让 P7 工作台待收款与本月收入在登记后自动反映新数据。
- 明确超额、重复提交、取消订单、退款、时间和历史流水边界。

## 已确定实现要求

### API 与只读数据

- `GET /api/admin/payments` 默认按 Asia/Shanghai 当前业务日期返回，也允许 `date=YYYY-MM-DD` 做确定性验证。
- 响应包含四项汇总、待收订单和收款流水，空库必须返回稳定空结构。
- 今日收款：收款状态为 `completed` 且 `paid_at` 位于业务日期上海时区边界内的金额合计。
- 待收款：订单未取消、付款状态非 `refunded` 且 `total_amount - paid_amount > 0` 的订单数。
- 本月收入：`completed` 收款在上海时区当月边界内的金额合计，与 P7 规则一致。
- 完成订单：所有 `order_status=completed` 的订单数，作为首版全量累计值；响应文案明确“累计完成订单”。
- 待收订单按服务开始日期、订单 ID 排序，返回订单 ID、客户姓名、小区、服务日期、猫咪数量、应收、已收、待收、付款状态与登记所需 revision。
- 收款流水按有效收款时间降序、ID 降序排列；无 `paid_at` 的既有 pending/refunded 记录排在最后。只返回客户姓名、订单/项目摘要、金额、方式、状态和时间，不返回备注。

### 登记收款

- `POST /api/admin/payments` 接收 `order_id`、正数且最多两位小数的金额、四种方式之一、带时区的收款时间、可选备注和 64 位 `expected_revision`。
- 客户 ID 必须由服务端从订单读取，前端不能提交或覆盖。
- “登记收款”只新增 `payment_status=completed` 的不可变流水；pending/refunded 仅兼容展示，不在本轮创建或变更。
- 允许同一订单多次部分付款；金额不得超过提交时待收金额，恰好付清后订单为 `paid`。
- 取消订单、订单付款状态为 `refunded`、已无待收金额、未知订单或旧 revision 必须拒绝；已完成但仍欠款的订单允许事后收款。
- 创建 Payment 与增加 `Order.paid_amount`、重新推导 `Order.payment_status` 必须同一事务完成。使用条件更新保护并发，冲突时整笔回滚，不能留下孤立流水或超额已收。
- P8 不静默扫描或改写历史不一致数据；从 P8 API 新增的每笔流水保证原子联动。

### 时间与 revision

- 统一使用固定 Asia/Shanghai（UTC+8）业务边界，避免 Windows 缺少系统 tzdata 时失败。
- API 输入收款时间必须明确携带时区并归一化为 UTC；SQLite 读取出的无时区值按既有 UTC 约定恢复；前端固定按 Asia/Shanghai 显示。
- 订单收款 revision 至少覆盖订单 ID、总额、已收、付款状态、订单状态和当前关联流水的 ID/金额/状态/时间，登记成功后返回新 revision。

### 前端

- `/admin/payments` 展示今日收款、待收款、本月收入、累计完成订单四张卡片。
- 页面展示“待收订单”和“收款记录”两部分，包含加载、错误、刷新和空状态。
- 顶部与每个待收订单都可打开登记表单；表单展示订单/客户/应收已收待收摘要，填写金额、方式、上海时间和可选备注。
- 金额默认当前待收值，前端做正数与不超额提示，后端仍是最终校验者。
- 成功后关闭表单并刷新汇总、待收列表和流水；失败保留表单与错误信息。
- P7 待收提醒跳转 `/admin/payments?action=create&order_id=<id>` 并自动选择对应仍待收订单；普通导航仍打开收款页面。
- 保持功能优先的轻量布局，不进行 P14 重度设计。

## 验收标准

- 空库、有待收订单和多条流水时，API 与页面均稳定可用且无静态假数据。
- 今日/本月上海时间边界、completed/pending/refunded 统计、累计完成订单与排序可由测试证明。
- 部分付款、连续多次付款、恰好付清会正确创建不可变流水并同步订单；P7 工作台和订单详情随之更新。
- 超额、零/负数、超过两位小数、取消/退款/结清订单、未知订单、旧 revision 和并发条件更新均不会产生部分写入。
- 批量响应不含电话、微信、详细地址、门禁、钥匙、备注、照片 URL、服务器路径或原始文件名。
- P8 没有实现退款、编辑、删除、网关或后续轮次功能。
- 后端全量测试、前端 lint/typecheck/全量测试/生产构建、`compileall`、Alembic current/check、`git diff --check` 全部通过。
- Windows 启停、临时 SQLite、API 代理联通与 1440×1000 浏览器可见验收通过；测试后端口和 P8 临时数据清理完成。
