# P10｜客户填写入口任务文件

## 背景

P0-P9 已完成 Windows 本地管理后台与手机轻量执行端。当前 `/fill/:token` 只有占位文案；数据库虽已预建 `customer_form_tokens` 与 `customer_form_submissions`，但尚无 Token 服务、填写 API、客户表单、后台审核入口，也没有“一条 Token 只能对应一份提交”及转换结果引用。

正式依据为《猫咪喂养登记系统-开发执行文档.md》第 3.3、7 节与 P10：客户通过专属链接填写联系人、地址、猫咪、服务日期、喂养要求和备注；提交后必须先进入待审核，只有后台确认后才能创建客户、猫咪与订单。当前仍以后台手工录入为主，二维码、PWA、完整鉴权和 UI 重构属于后续轮次。

## 目标

- 建立随机、不可顺序猜测、可设置有效期且可启用/关闭的客户填写 Token。
- 将 `/fill/:token` 升级为可保存草稿、提交一次并显示结果的响应式客户表单。
- 在客户档案下增加 `/admin/intake` 次级入口，用于生成/复制链接、管理链接状态、查看提交摘要和单条敏感详情。
- 提交只进入待审核，不自动写入正式客户或订单。
- 后台确认时，以一个数据库事务创建 Customer、多只 Cat、待确认 Order 及每日 Task，并记录转换结果；失败必须整体回滚，重复确认不得重复创建。
- 保持 Windows 本地可运行和 admin/mobile/fill 清晰分区，不引入真实数据或公网依赖。

## 禁止修改范围

- 不实现二维码、短信/邮件发送、支付或收款链接。
- 不实现 P11 的 manifest、Service Worker、离线能力或安装提示。
- 不实现 P12 的登录、会话、角色权限、Token 哈希、防刷、Tunnel 或公网部署；但 P10 必须完成随机性、有效期、关闭、数据隔离与输入校验基础。
- 不实现 P13 全项目专项校验或 P14 重度 UI/UX 重构。

- 不新增依赖、不更换技术栈、不做无关大规模重构。

## 已确定实现要求

### 数据模型与 Token 生命周期

- 新增迁移 `0004_customer_intake_conversion`：`customer_form_submissions.token_id` 增加唯一约束；Submission 增加 `reviewed_at`、`converted_at`、可空 `converted_customer_id` 与 `converted_order_id`，后两者分别引用 Customer/Order 并使用 `ON DELETE SET NULL`。
- 每个 Token 最多一份 Submission；Submission 从 `draft` 进入 `submitted` 后，公开端不得再覆盖。
- 后台以 Python `secrets.token_urlsafe(32)` 生成 Token，数据库唯一冲突时有限重试；不使用顺序 ID、时间戳或伪随机数构造链接。
- 后台创建 Token 时设置 1-90 天有效期，默认 14 天；返回相对 `fill_path`，前端在浏览器内拼接当前 Origin 后复制，不在数据库保存本机域名。
- Token 可在未提交且未过期时 `active ↔ disabled`；已经过期的 Token 不得恢复，已提交的 Token 不得恢复编辑。到期状态由服务端统一判断并惰性落库为 `expired`，对应草稿同时标为 `expired`。
- 公开端对格式错误或未知 Token 统一返回 404；disabled/expired 返回 410；submitted/reviewed/converted 返回不含 Payload 的只读状态，不能继续保存。
- P10 仍将随机 Token 原文存库以适配既有模型与本地部署；Token 哈希、正式身份鉴别与防刷明确留给 P12。

### 表单、校验与隐私

- 公开命名空间为 `/api/fill/{token}`：GET 读取当前表单状态，PUT 保存草稿，POST `/submit` 完整校验并一次性提交。
- 表单包含客户姓名、微信/手机至少一种联系方式、小区与详细地址、楼栋/单元/房号、门禁方式与入户说明、钥匙状态/编号、客户备注；至少一只猫咪及其饮食、猫砂、用药、特殊情况和服务注意事项；服务起止日期、每日次数、至少一个标准服务事项及订单备注。
- 完整提交复用并收紧既有 Customer/Cat/Order 字段长度、年龄、日期 1-366 天、每日 1-10 次与服务事项枚举约束；草稿允许缺少最终必填字段，但仍限制字段类型、长度、猫咪最多 20 只及未知字段。
- 表单不包含价格、订单状态、正式记录 ID 或图片上传。后台转换统一使用当前默认基础单价、0 元爬楼费、0 元其他费用、未收款和 `pending_confirmation`。
- 公开 GET 仅在可编辑草稿状态返回当前 Token 自己的草稿；提交后只返回状态与通用成功文案。公开 422 错误只返回字段位置、类型与提示，不得包含 `input`、`ctx` 或回显 Payload。
- 后台列表只返回姓名、小区、猫数量、服务日期和状态摘要；手机号、详细地址、门禁、钥匙及完整猫咪要求只在选中单条详情后返回。
- 服务端不得把 Token、Payload、手机号、地址、门禁或钥匙信息主动写入日志；Uvicorn 访问日志中的 `/api/fill/:token` 段必须脱敏为 `[redacted]`。

### 后台审核与原子转换

- 后台命名空间为 `/api/admin/intake`：创建/列表/修改 Token，列表/读取 Submission，标记已审核，确认转换。
- Token 状态修改、Submission 审核和确认转换均携带基于服务端状态生成的 SHA-256 `revision`；旧 revision 返回 409，避免两个后台页面互相覆盖。
- 标记审核只允许 `submitted → reviewed`；确认转换允许从 `submitted` 或 `reviewed` 开始。
- 转换时重新以正式完整 Schema 校验数据库 JSON，不信任历史 Payload；再通过条件更新抢占待转换状态，阻止并发重复转换。
- 转换链必须在同一 Session/事务中完成：创建 Customer（正确设置 geocode 状态）→ 创建 Cats → flush IDs → 按默认计价创建待确认 Order/OrderCat → 生成每日 Tasks/TaskItems → 写入转换引用与 `converted_at` → 一次 commit。
- 转换失败必须 rollback，Submission 恢复原可审核状态且不得留下半套 Customer/Cat/Order/Task。重复调用已转换记录时幂等返回既有 Customer/Order 引用，不创建重复记录。
- 客户、订单原有手工创建接口应复用新抽取的“只构造、不提交”服务，原响应、计价、任务生成和状态规则保持不变。

### 前端

- `/fill` 无 Token 时继续给出明确错误；`/fill/:token` 提供加载、无效、已关闭/过期、可编辑草稿、提交成功和请求失败状态。
- 公开表单按“联系与地址 → 猫咪 → 服务计划 → 确认提交”分区，支持增删猫咪、保存草稿、最终提交；提交前给出“提交后需后台审核且不可继续编辑”的明确提示。
- 表单针对至少 320px 宽度设计，标签、错误和按钮适合手机操作；不加载管理后台侧栏，不显示内部 ID、Token 原文或价格。
- `/admin/intake` 作为客户档案的次级页面，不增加第六个主导航项。客户档案页头新增“客户填写”入口。
- 后台页面支持有效期天数生成链接、复制完整链接、启用/关闭未提交 Token、查看摘要/详情、标记已审核和确认生成客户与待确认订单。
- 转换按钮必须二次确认，操作期间禁用重复点击；成功后显示并链接到客户档案和订单计划，不在前端自行拼装正式记录。
- 不实现二维码、复杂筛选、批量操作或重度视觉设计。

## 验收标准

- Token 长度/随机性、唯一性、1-90 天有效期、关闭/恢复、过期不可恢复与惰性过期均有自动化证据。
- 未知/格式错误 Token 不可枚举；公开 API 只能访问当前 Token 的草稿，提交后不能覆盖，也不能读取其他表单或后台字段。
- 草稿、完整提交、多猫、联系方式、日期、次数、服务事项、长度与未知字段校验有测试。
- 后台列表隐私最小化，详情才返回手机号、完整地址、门禁、钥匙和猫咪要求。
- 提交本身不增加 Customer/Order；只有后台确认后才一次创建一位 Customer、多只 Cat、一张 pending_confirmation Order 及完整 Tasks。
- 重复/并发提交与重复/并发转换不生成重复记录；旧 revision 返回 409；转换中注入失败后所有正式记录回滚。
- 原客户和订单手工创建、计价、Task 生成无回归。
- 新迁移可在空 SQLite 升级/降级/再升级，Alembic current/check 无漂移，并保持 PostgreSQL 兼容的标准类型与约束。
- `/fill/:token` 在 390×844 无横向溢出，能够用虚构资料保存草稿并提交；`/admin/intake` 能生成/复制链接、查看提交和确认转换。
- 后端全量测试、前端 lint/typecheck/全量测试/生产构建、`compileall`、Alembic current/check、`git diff --check` 全部通过。
- Windows 临时 SQLite 与本地启停/API 代理联通验收通过；测试后端口、临时数据库和本轮测试数据完整清理。
- P10 未实现 P11-P14、未新增依赖、未提交 Token/Payload/数据库/日志/真实敏感数据。
