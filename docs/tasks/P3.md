# P3｜订单系统执行任务

## 背景

P0–P2 已建立 Windows 本地管理后台、数据库与迁移机制，以及客户和多猫档案闭环。正式开发文档要求 P3 创建订单时录入客户、猫咪、日期范围、每日次数、服务内容、价格和备注，并自动计算服务次数、费用及每日任务。现有 `orders`、`order_cats`、`tasks`、`task_items` 模型已能覆盖本轮，无需新增数据库字段。

## 目标

1. 建立本地后台订单列表、新增、查看和安全编辑 API。
2. 建立统一、可测试的服务次数与订单计费逻辑。
3. 创建订单时在同一事务中自动生成每日任务和任务事项。
4. 在现有 `/admin/plans`“订单计划”入口完成订单管理页面，并兼容 `/admin/orders` 直达跳转。
5. 保护已开始、已完成或已有照片的任务历史，不因普通订单编辑被重建删除。
6. 通过自动测试和 Windows 临时数据库验证 7 天订单自动生成 7 个任务，以及每天多次服务场景。

## 允许修改范围

- `backend/app/api/orders.py`：P3 订单 HTTP 路由。
- `backend/app/schemas/order.py`：订单请求、响应和表单选项模型。
- `backend/app/services/orders.py`：计费、校验、任务生成与历史保护。
- `backend/app/main.py`：挂载订单 Router。
- `backend/tests/`：订单服务与 API 测试。
- `frontend/src/features/orders/`：订单 API、类型、表单、列表和详情组件。
- `frontend/src/pages/admin/`、`frontend/src/routes/`：接入订单页面与兼容路由。
- `README.md`、`DEVELOPMENT_PROGRESS.md` 和本任务文件。

## 禁止修改范围

- 不新增左侧一级导航，保持“工作台、订单计划、客户档案、收款记录、设置”。
- 不实现 P4 按天排程、计划时间、拖拽排序、任务状态操作或三栏地图布局。
- 不实现 P5 地图路线、P6 执行/照片上传、P8 收款流水或 P9 手机执行端。
- 不实现 P10 客户填写、P11 PWA、P12 完整鉴权/公网访问或 P14 重度 UI 重构。
- 不允许浏览器提交或覆盖 `total_amount`；应收必须由后端权威计算。
- 不删除订单，不在存在执行历史时删除重建任务、任务事项或照片。
- 订单响应不得嵌套手机号、详细地址、门禁、钥匙或客户备注。
- 不提交真实客户/订单数据、数据库、照片、`.env`、日志或运行时文件。

## 已确定实现要求

- 页面继续使用 `/admin/plans`；`/admin/orders` 仅重定向到该入口。
- API 使用 `/api/admin/orders` 前缀，仅供本地后台使用，不得直接公开到公网。
- 日期范围包含开始日和结束日：`service_days = end_date - start_date + 1`。
- `total_visits = service_days × visits_per_day`；每日次数限制为 1–10，日期范围最多 366 天，防止误操作生成异常数量任务。
- 当前收费规则固定为：默认基础价 30 元/次；每只额外猫 5 元/次；四层及以上爬楼 5 元/次；其他费用按整单一次计入。
- `extra_cat_fee = max(猫咪数 - 1, 0) × 5`。
- `total_amount = (base_price + extra_cat_fee + stairs_fee) × total_visits + other_fee`。
- `due_amount = max(total_amount - paid_amount, 0)`；P3 新订单 `paid_amount=0`、`payment_status=unpaid`，实际收款流水留给 P8。
- 金额使用 Decimal 且最多两位小数；基础价可在订单表单调整，爬楼费使用 0/5，其他费用为非负整单金额。
- 至少选择一只属于该客户且在档的猫咪；不得重复选择。编辑历史订单时，可继续保留该订单原已关联、后来被停用的猫咪，但不得新加入其他停用猫咪。
- 至少选择一个受 `TaskItemType` 约束的服务事项，去重后稳定保存。
- 创建订单、关联猫咪、生成任务和任务事项必须在一个数据库事务中完成；失败时整笔回滚。
- 每个日期按 `visits_per_day` 生成相应数量任务，`sort_order` 为当天第几次服务（从 0 开始），P4 再设置具体时间与人工排序。
- 每个任务按订单服务内容生成必做、未完成的 `task_items`。
- 新订单只允许“待确认”或“已确认”；任务初始状态分别为 `pending` 或 `confirmed`。
- 编辑日期、每日次数、客户、猫咪或服务内容时，仅当全部任务均未开始、未完成、无异常、无执行时间、无照片且事项未勾选时，才可事务化重建任务；否则返回 `409`。
- 更换已有收款记录订单的客户返回 `409`，防止付款记录与客户错配。
- 取消订单时只取消尚未执行的任务；恢复为待确认/已确认时只同步未执行任务。订单标记完成必须等待全部任务完成。
- 列表与详情只返回客户姓名、小区及猫咪档案摘要；不返回客户敏感详情。
- 订单表单选项 API 只返回客户 ID、姓名、小区及在档猫咪 ID/名称。
- 本轮不新增迁移；总服务次数和待收金额作为可验证派生值返回。

## 验收标准

1. 创建 10 月 1 日至 10 月 7 日、每天 1 次的订单后，数据库恰好生成 7 个任务。
2. 创建跨 3 天、每天 2 次的订单后生成 6 个任务，每天各 2 个，且每个任务包含所选服务事项。
3. 两只猫、基础价 30 元/次、无爬楼、无其他费用时，每次加价 5 元，7 次应收 245 元。
4. 三只猫、爬楼、其他费用场景按确定公式准确计算，浏览器不能伪造总额。
5. 可以查看订单列表、详情、任务数量和费用明细，并编辑尚未执行订单。
6. 已有执行历史时结构性编辑返回 `409`，原任务、事项和照片不丢失。
7. 跨客户猫咪、停用猫咪、重复猫咪、空服务、非法日期/次数/金额返回明确的 `404`/`422`。
8. 订单 API 响应不泄露手机号、详细地址、门禁、钥匙或客户备注。
9. Windows 本地环境通过前端代理完成创建订单、自动生成任务、编辑状态和读取详情。
10. P0–P2 的健康检查、迁移、Seed、客户档案、前端路由及 Windows 启停保持通过。
