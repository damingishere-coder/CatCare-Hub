# P27 数据一致性护栏

## 背景

第二次工程复检确认，当前仍值得处理的最高优先级风险集中在订单、任务、地理编码和演示数据清理的数据一致性边界。本任务是既定三阶段整改计划的第一阶段，必须保持为单独、可审查、可回滚的 PR。

## 目标

- 为订单写入增加幂等键与乐观并发控制。
- 为任务执行增加数据库级条件更新，避免并发请求静默覆盖。
- 让订单执行状态由任务执行结果驱动，并收紧人工状态迁移。
- 在地理编码失败时清除失效坐标及未执行任务的计划坐标。
- 精确标记演示数据，混入非演示依赖时拒绝清理。
- 让本地迁移入口执行 SQLite 备份和完整性检查，并拒绝盲目升级非 SQLite 数据库。

## 允许修改范围

- `backend/app/models/`、`backend/app/schemas/`、`backend/app/api/`、`backend/app/services/`、`backend/app/db/`

- 生产数据库、远程服务器、密钥、环境变量内容
- 审计报告与 Codemap 产物

## 已确定实现要求

1. 新迁移同时兼容 SQLite 和 PostgreSQL，为演示客户、猫咪、订单、任务、任务事项、任务照片和收款新增来源标记，并新增订单写版本、任务执行版本、订单幂等键和请求哈希。
2. 演示数据历史回填只能匹配完整且唯一的内置指纹；无法确认时保持未标记。
3. 创建订单要求 `Idempotency-Key`；同键同载荷重放原结果，同键不同载荷返回 `409`。
4. 订单变更要求 `If-Match`，使用条件 `UPDATE` 预占新版本；并发冲突返回 `409`，不得留下部分写入。
5. 任务执行使用条件 `UPDATE` 同时保护任务与所属订单；订单的 `in_progress`、`completed` 仅由任务状态派生。
6. 客户或来源变更属于结构性变更；存在执行证据或收款时返回 `409`，允许时必须原子同步订单快照、猫咪关联、联系方式和任务。
7. 地理编码失败必须清除订单旧坐标、定位指纹和未执行任务的计划坐标；已执行任务的实际证据不得更改。
8. 清理演示数据前发现任何未标记依赖时返回 `409`，且删除数为零。
9. 手动迁移统一经过预检：SQLite 先备份，迁移前后执行完整性和外键检查；本地脚本对非 SQLite 数据库拒绝盲目升级。

## 验收标准

- 并发订单写、并发任务写均只能有一个成功，另一个稳定返回 `409`。
- 创建订单在响应丢失后可使用同一幂等键安全重试，不产生重复订单。
- 状态历史、任务执行证据和订单派生状态一致。
- 地理编码失败不保留可被误用的旧计划坐标。
- 纯演示数据可清理；混合数据不删除任何记录。
- 全量后端测试、前端测试、lint、类型检查和构建通过。
- Git diff 不包含范围外修改、敏感信息、调试代码或临时产物。
