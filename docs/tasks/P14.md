# P14 UI Design 重构执行任务

## 背景

P0-P13 已完成并通过真实业务闭环、权限隔离、数据验证和全量回归。当前界面功能完整，但视觉主要由页面内重复 Tailwind class 维持，缺少统一的语义 Token、页面标题、按钮、表面、反馈状态和表单语言。正式开发文档要求本轮在不改变业务逻辑的前提下，整体重构 UI、UX、布局、Design System、视觉层级、交互细节与响应式。

## 目标

1. 建立克制、现代、Windows 本地友好的 Design System，不引入远程字体、图片或新 UI 框架。
2. 统一后台 Shell、页面标题、按钮、表单、面板、指标、状态、表格、弹窗和空/错/加载状态。
3. 强化“按天计划 + 地图路线 + 右侧任务/客户信息”三栏核心布局和信息层级。
4. 统一 PC 执行、手机执行、登录和公开填写体验，并保持 320px 起的响应式与触摸目标。
5. 保留所有业务状态机、权限、API、隐私边界、可访问名称与自动化测试契约。

## 视觉方向

- 简洁、高级、大气、克制、现代，接近高质量消费级 SaaS。
- 中性浅灰背景、白色内容面、深 navy/slate 文字，低饱和 indigo 作为有限主行动色。
- amber 仅表达提醒，red 仅表达危险/异常，emerald 仅表达成功/完成。
- 通过留白、排版和表面层级减少描边堆叠；阴影只用于 Shell、浮层和关键表面。
- 中等圆角：控件 8-10px、面板约 12px；圆形只用于状态、序号与图标，不堆叠 2xl 圆角。
- 不使用传统国产后台式密集边框、高饱和橙色、大量装饰、过度萌宠图形或花哨渐变。

## 允许修改范围

- `frontend/src/styles.css`：语义 Token、基础元素、动画、安全区域和复用视觉类。
- `frontend/src/components/ui/`：只包含纯呈现/可访问性组件。
- `frontend/src/layouts/`、`frontend/src/features/**/*.tsx`、`frontend/src/pages/**/*.tsx`：布局与视觉 class 重构。
- `frontend/src/**/*.test.tsx`：仅在新增纯呈现组件需要时补测试；不得放宽既有业务断言。
- `README.md`、`DEVELOPMENT_PROGRESS.md`、`docs/tasks/P14.md`：记录 P14 结果。

## 禁止修改范围

- 不修改后端、数据库、迁移、业务 API、前端 API/type、认证、状态机、费用、排程 revision 或 PWA 缓存边界。
- 不新增依赖、远程字体、图片素材、分析脚本或外部 Design 服务。
- 不改变路由 URL、按钮/字段可访问名称、heading 业务标题、dialog/alert/article 语义和现有隐私展示范围。
- 不增加设置业务、导出、退款、离线写队列或其他功能。
- 不读取或提交真实 `.env`、业务数据库、客户资料、照片、日志或运行数据。

## 已确定实现要求

### Design System 与公共呈现

- 在全局样式定义背景、内容面、文字、边界、行动、焦点和状态语义变量，并提供 reduced-motion 降级。
- 提供 `PageHeader` 统一 eyebrow、标题、说明和操作区；保留页面原有 heading 文本/ID。
- 提供少量 `cc-*` 语义视觉类统一 surface、button、field、metric、empty/loading/error，不承载业务判断。
- 表单输入保持清晰焦点、禁用态和最小触摸高度；弹窗保留遮罩、标题、取消/确认顺序与危险操作区分。

### 后台 Shell 与核心页面

- AdminLayout 在桌面保持左侧导航，在小屏保持可横向访问的顶部导航；保留五项导航与退出。
- 工作台降低卡片边框密度，突出今日指标、快捷动作、安排和提醒。
- 订单计划在 1280px 以上保持左 320px / 中间自适应地图 / 右 360px；1024px 附近自然纵向且保存区可达。
- 地图、日期/任务选中态、脏状态、路线推荐、锁定、进入执行和任务详情联动保持原逻辑。
- 客户/订单主从页、收款表格、后台填写审核和 PC 执行页使用一致的层级与操作语义。

### 手机、公开填写与认证

- 手机今日与单任务页保持 44px 触摸目标、safe-area、无横向滚动，现场主操作视觉优先。
- 公开填写页将长表单分为清晰章节，保留 Token 状态、草稿、提交、字段 label 与多猫 article 语义。
- 登录、无权限、404 与设置占位页使用统一品牌/反馈视觉；访问码与安全提示不弱化。

## 验收标准

1. 所有主要页面视觉语言统一，主/次/危险/禁用操作和成功/提醒/异常状态清晰。
2. 1440×900 与 1280×800 下后台 Shell 和计划三栏无横向溢出；三栏业务顺序和操作完整。
3. 1024×768 下计划、客户、订单、执行页可纵向使用，关键保存/执行按钮可达。
4. 390×844、375×812 与 320px 下 login、mobile、mobile task、fill 无横向溢出，触摸目标可用。
5. 客户、订单、收款、今日任务的批量隐私边界不变；现场敏感信息仍只在受保护详情展示。
6. 现有 22 个前端测试文件及全部测试通过；lint、typecheck、build 通过，无依赖或业务代码变化。
7. 真实浏览器检查 console、页面标题、导航、空/加载/错误状态和核心交互；只使用隔离临时数据库/虚构账号。
8. Git diff 不含后端、API/type、PWA、依赖锁、数据库、上传、`.env`、日志、临时或真实资料。

## 测试命令

```powershell
npm run lint --prefix frontend
npm run typecheck --prefix frontend
npm test --prefix frontend -- --run
npm run build --prefix frontend
git diff --check
git status --short
git diff --stat
```

浏览器验收使用隔离临时 SQLite、虚构 access code 和临时上传目录；不得触碰默认业务数据库或真实 `.env`。

## 返回格式

Operator 只返回：

1. `summary`：成功或失败，以及是否修改源文件。
2. `commands`：每条命令、退出码、测试数量、构建模块数和警告。
3. `visual_contracts`：Shell、三栏、桌面/平板/手机视口和状态视觉证据。
4. `regression_boundaries`：路由、交互、可访问名称、隐私和 PWA/API 未变证据。
5. `git_scope`：实际修改范围、依赖与敏感文件检查。
6. `verdict`：只陈述验证事实，不代替主代理最终验收。
