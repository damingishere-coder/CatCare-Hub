# 猫咪喂养登记系统｜开发执行文档

> **历史档案**：这是项目早期的设计与执行依据，其中部分访问边界和功能计划已被后续实现替代。请以[项目状态](../PROJECT_STATUS.md)、专题文档、当前代码和自动化测试为准。

> 项目定位：面向个人上门喂猫业务的轻量级业务管理系统。  
> 当前阶段优先级：**功能闭环 > 数据结构 > 使用效率 > UI 精修**。  
> UI 当前只要求简洁、清晰、可用；待核心功能稳定后，再单独使用 Design 能力进行整体视觉重构。

---

# 1. 项目目标

本项目用于替代原有 Excel 管理方式，将上门喂猫业务中的：

- 客户
- 猫咪
- 订单
- 每日任务
- 路线安排
- 收款
- 客户填写信息

统一沉淀到一个本地 Web 系统中。

当前产品主要服务于一个人使用，不按复杂企业 SaaS 设计。

---

# 2. 当前产品形态

整体采用：

**一个后端 + 一个数据库 + 三种访问界面**

```text
                    猫咪喂养登记系统
                           │
                    后端 API + 数据库
                           │
          ┌────────────────┼────────────────┐
          │                │                │
      电脑管理后台        手机执行端        客户填写端
        /admin           /mobile          /fill/:token
```

---

# 3. 三端定位

## 3.1 电脑管理后台

主要用于重操作。

包括：

- 客户管理
- 猫咪档案
- 新建订单
- 多日订单安排
- 按天生成执行任务
- 地图路线规划
- 收款记录
- 提醒
- 数据查询
- 系统设置

电脑后台是当前第一优先级。

---

## 3.2 手机执行端

手机端不是完整后台。

只保留上门执行过程中真正需要的能力：

- 查看今天任务
- 查看当天路线
- 查看客户地址
- 一键导航
- 查看猫咪资料
- 查看服务要求
- 查看门禁 / 钥匙信息
- 勾选服务事项
- 上传照片
- 填写本次备注
- 标记任务完成

后续以 Responsive Web / PWA 方式实现，不优先开发原生 App。

---

## 3.3 客户填写端

当前业务仍以：

**后台手动录入为主**

但系统从第一版开始预留：

```text
/fill/:token
```

客户填写入口。

后台可以：

- 生成客户填写链接
- 复制链接
- 后续生成二维码
- 查看客户提交的信息
- 将客户提交内容转为正式客户 / 订单

客户端以后可以自行填写：

- 客户基础资料
- 联系方式
- 地址
- 门禁
- 猫咪信息
- 喂养要求
- 服务日期
- 备注


## C. 路线排序

第一阶段：

- 用户手动排序
- 根据列表顺序显示地图路线

第二阶段：

- 计算距离
- 计算行驶时间
- 给出推荐顺序
- 支持一键采用推荐路线

注意：

**不要第一版就自行开发复杂路径算法。**

尽量使用地图服务提供的路线规划 API。

# 7. 客户填写入口

客户档案页面右侧保留：

```text
客户填写入口
```

后台支持：

- 生成链接
- 复制链接
- 生成二维码（后续）
- 设置链接状态
- 查看提交记录

URL 结构：

```text
/fill/:token
```

例如：

```text
/fill/A8F32Kxxxx
```

---

## Token 基本要求

Token：

- 随机生成
- 不可顺序猜测
- 可设置有效期
- 可以关闭
- 不允许访问其他客户数据

---

## 客户提交状态

建议：

```text
draft
submitted
reviewed
converted
expired
```

客户提交后：

不要自动直接成为正式订单。

后台显示：

```text
新客户资料待确认
```

由用户确认后：

```text
创建客户
创建猫咪
创建订单
```

# 8. 订单自动生成执行任务

这是核心业务逻辑。

例如创建订单：

```text
客户：张女士
日期：10月1日 - 10月7日
每天：1次
```

系统应该自动生成：

```text
10月1日 1个任务
10月2日 1个任务
10月3日 1个任务
10月4日 1个任务
10月5日 1个任务
10月6日 1个任务
10月7日 1个任务
```

共 7 个执行任务。

---

## 每天多次情况

例如：

```text
每天2次
```

系统生成：

```text
上午任务
下午 / 晚上任务
```

初始时间可以允许用户手动设置。

# 27. Codex 执行原则

Codex 开发时必须：

1. 先阅读当前代码。
2. 先理解现状再修改。
3. 优先复用现有组件。
4. 不重复造已有功能。
5. 不擅自更换框架。
6. 不擅自大规模重构。
7. 每轮完成后自己运行测试。
8. 修复错误后再次测试。
9. 确认成功后再进入下一轮。
10. 保证 Windows 可运行。
11. 所有文件路径使用跨平台方式。
12. 所有关键行为必须有错误处理。
13. 不为了“看起来完成”而写假数据或静态按钮。

# 30. 当前产品原则

最后统一强调：

这个项目不是大型 SaaS。

目标不是功能越多越好。

目标是：

```text
接单之后不再翻 Excel
每天打开系统就知道去哪
手机到了客户家就知道做什么
做完可以直接记录
钱有没有收一眼就知道
客户信息下一次还能直接复用
```

所有开发决策都以此为准。
